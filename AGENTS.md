# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Ethereum P2P Observatory: real-time insights into Ethereum's peer-to-peer layer. The stack is Bun throughout. No Python, no Jupyter notebooks, no Astro.

1. `observatory/` (Bun): fetches ClickHouse telemetry, writes Arrow files, generates the chart registry manifest
2. `site/` (Vite + React + ECharts): interactive chart workspace served as a static site
3. Deployed to Cloudflare R2 via content-addressed storage

## Common commands


## Bun observatory pipeline

`observatory/` is a self-contained Bun package. Key entry points:

- `bun run fetch [--date YYYY-MM-DD] [--config path]`: fetches all registered queries for all dates in the config window, writing Arrow files to `build/data/`.
- `bun run manifest`: generates `site/public/registry.json` by scanning `site/src/workspace/charts/topics.ts` for `TOPIC_REGISTRY` entries.
- `bun run upload`: hashes files in `site/dist/`, deduplicates against R2 via `ListObjectsV2`, uploads new blobs with immutable cache headers, then writes a path-to-blob manifest at `R2_MANIFEST_KEY`.

Config is read from `observatory/pipeline.v2.yaml` by default (overridable via `--config`).

## Chart authoring flow (defineChart)

Charts live in `site/src/workspace/charts/<topic>/`. Each chart file exports a chart definition using `defineChart`:

```ts
import { defineChart } from '@/workspace/charts/define';

export const myChart = defineChart({
  id: 'my-chart-id',
  title: 'My chart',
  queries: ['query_id'] as const,
  render(tables, opts) {
    // tables['query_id'] is an Apache Arrow Table
    // Return an EChartsOption
    return { series: [...] };
  },
});
```

Topics group related charts and are registered in `site/src/workspace/charts/topics.ts` via `TOPIC_REGISTRY`. Running `just manifest` re-scans topics and regenerates `site/public/registry.json`.

## Staleness via AST hash of query source

`observatory/src/staleness.ts` hashes each query function's AST (stripping comments and position data) using Babel's parser. The hash is stored in `build/data/manifest.json` alongside per-date fetch metadata.

When `just fetch` runs, it compares current hashes to stored hashes. Any query whose hash has changed is considered stale and is re-fetched for all dates in the window.

The manifest schema:

```json
{
  "schema_version": "2.0",
  "dates": ["2025-12-17"],
  "latest": "2025-12-17",
  "query_hashes": { "blobs_per_slot": "7779ed745ea1" },
  "date_queries": {
    "2025-12-17": {
      "blobs_per_slot": { "fetched_at": "...", "query_hash": "...", "row_count": 7200 }
    }
  }
}
```

## Adding a new chart

1. Create a query in `observatory/src/queries/<topic>/my_query.ts`:

   ```ts
   import { defineQuery } from '../registry';

   export const myQuery = defineQuery({
     id: 'my_query',
     outputFile: 'my_query.arrow',
     fetch: async (client, date, network) => {
       // Execute SQL, return Arrow table rows
     },
   });
   ```

2. Register it in `observatory/src/queries/index.ts` (import and add to `QUERY_REGISTRY`).

3. Create a chart in `site/src/workspace/charts/<topic>/my_chart.ts` using `defineChart` with `queries: ['my_query'] as const`.

4. Register the chart in its topic in `site/src/workspace/charts/topics.ts`.

5. Run `just manifest` to regenerate `site/public/registry.json`, then `just fetch` to pull data.

## Design preferences

**Full design context is in `.impeccable.md`. Read it before any UI work.** It specifies palette, typography, spacing, components, accessibility, and anti-patterns in detail. The rules below are the short list; `.impeccable.md` is authoritative where they overlap.

- **Simplicity**: prefer removing features over adding complexity. When in doubt, simplify.
- **No rounded corners**: `--radius: 0` globally; never use `rounded-*` classes.
- **No inline SVG**: use `Icon.tsx` with Lucide icon names.
- **No date pickers**: use prev/next navigation instead.
- **No emojis** unless explicitly requested.
- **Centralized config**: all pipeline config in `observatory/pipeline.v2.yaml`.
- **Explicit skip logging**: data pipeline should explicitly log `SKIP` vs `Fetching`.
- **Rebasing preference**: prefer rebasing work on `main` before PR creation.
- **Git style**: use [conventional commits](https://www.conventionalcommits.org/) for all changes.
- **No em dashes in any documentation**: use colons, parentheses, commas, semicolons, or separate sentences.
- **Sentence case for all headings** in markdown and generated docs.

## Code conventions

### TypeScript

- Strict mode with `noUncheckedIndexedAccess: true` in both packages.
- No `as any`. Use discriminated unions and Zod for runtime validation at boundaries.
- No non-null assertions (`!`). Use optional chaining and nullish coalescing.
- Prefer `as const` objects over `enum`.
- Date format: `YYYY-MM-DD`.

### React / site

- React components (`.tsx`) for all interactive elements.
- Prefer CSS variables over hardcoded colors.
- **DRY utilities**: before adding helper functions, check `site/src/lib/utils.ts` first. Add new utilities there if they will be used in multiple components.

### Adding shadcn/ui components

```bash
cd site && bunx shadcn@latest add <component-name>
```

After adding, strip all `rounded-*`, `shadow-*`, and `ring-*` classes from the generated source (per `.impeccable.md` and ERRATA entries for Plan 01 Task 09).

## Debugging

### Data fetch issues

- Verify `.env` has valid ClickHouse credentials (`CLICKHOUSE_URL`, `CLICKHOUSE_USERNAME`, `CLICKHOUSE_PASSWORD`).
- Run `bun run --cwd observatory fetch --date YYYY-MM-DD` for a specific date.
- Check `build/data/manifest.json` for fetch metadata.

### Site build issues

- Run `just manifest` first to ensure `site/public/registry.json` exists.
- Run `bun run --cwd site build` for detailed Vite errors.

## CI/CD

Two separate workflows:

- **`ci.yml`**: runs on push to main and all PRs. Typechecks, lints, tests (unit + e2e), and builds both packages.
- **`deploy.yml`**: runs on push to main and manually. Fetches data, generates manifest, builds site, uploads to R2.

## R2 deployment

Site deployed to Cloudflare R2 with content-addressed storage (CAS):

```
r2-bucket/
├── blobs/                    # Immutable content-addressed files
│   ├── {sha256}.html
│   └── {sha256}.js
└── manifests/
    ├── main.json             # Production manifest (path -> blob key)
    └── pr-14.json            # PR preview manifest
```

Serving logic:
1. Worker receives request for a path (e.g., `/`)
2. Loads `manifests/main.json` (cached 60s in worker)
3. Resolves path to blob key (e.g., `blobs/abc.html`)
4. Serves blob with appropriate headers:
   - HTML: `Cache-Control: public, max-age=0, must-revalidate`
   - Assets: `Cache-Control: public, max-age=31536000, immutable`

Domains:
- Production: `observatory.ethp2p.dev`
- PR previews: `observatory-staging.ethp2p.dev/pr-{number}/`

Key files:
- `observatory/src/upload.ts`: CAS upload CLI (blob deduplication via SHA256)
- `worker/src/index.ts`: Cloudflare Worker (manifest resolution, blob serving)
- `worker/wrangler.toml`: Worker config (routes, R2 binding)
